## Context

Руководство уже объясняет работу с несколькими провайдерами через CLIProxyAPI. Новый маршрут проходит через Google Antigravity и не равнозначен прямому доступу к Anthropic, Gemini API или корпоративному Google Cloud. Контракт пользователя описан в `specs/ai-access-guide/spec.md`.

## Goals / Non-Goals

**Goals:** дать проверяемую инструкцию с понятными условиями и не гарантировать неподтверждённую совместимость или доступность моделей.

**Non-Goals:** менять прокси, регистрировать аккаунты от имени пользователя или обходить ограничения регионов, квот и условий сервисов.

## Decisions

1. **Описывать фактические тарифы Google AI Pro и Ultra без цен и других денежных сумм.** «Max» не использовать как название тарифа Google без подтверждения: это может ввести читателя в заблуждение. На момент подготовки [документация Antigravity](https://antigravity.google/docs/plans/) указывает обновление квоты Pro каждые пять часов до недельного лимита, а доступ к сторонним моделям явно перечисляет для Ultra; право Pro на Claude требует отдельной проверки. Предупредить, что по личному опыту пользователя квота Pro на Opus может исчерпаться уже через несколько минут; это не гарантированный лимит. Для Ultra приводить только подтверждённые условия. Никаких точных чисел запросов без первичного источника.
2. **Разделить доступность модели в сервисе, техническую поддержку прокси и разрешение на такой способ доступа.** [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) заявляет поддержку Antigravity; это не доказывает разрешённость стороннего подключения или наличие конкретной модели в аккаунте. Если разрешённость, конкретные команды либо модель не подтверждены, честно обозначить границу и не выдавать маршрут за гарантированно работающий. [Анонс Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/claude-opus-55-and-claude-sonnet-55-available-in-antigravity) относится к корпоративным клиентам и сам по себе не подтверждает персональные тарифы.
3. **Дополнить существующие разделы и схему, а не создавать параллельное руководство.** Следовать текущей структуре README и `docs/`; проверить, какие из последовательных схем тоже затронуты новым маршрутом. В README поставить первым пунктом «Одна труба для моделей разных провайдеров» с существующим пояснением.
4. **Согласовать изображение схемы с пользователем.** После обновления схемы попросить пользователя прислать новый скриншот для README и не отмечать соответствующую задачу выполненной до его получения и проверки. Исходники схем и опубликованные копии проверять совместно.

## Risks / Trade-offs

- [Доступность и квоты быстро меняются] → ссылаться на первоисточники и указывать дату проверки, не обещать модели и фиксированные лимиты.
- [Сторонний OAuth может противоречить условиям] → проверять действующие условия и явно обозначать неопределённость; техническую поддержку не считать разрешением.
- [Скриншот зависит от пользователя] → работа по нему останавливается до получения, остальные независимые проверки можно выполнять параллельно.
